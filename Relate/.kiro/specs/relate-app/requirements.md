# Requirements Document

## Introduction

Relate is a full-stack web application that helps people understand difficult or abstract concepts by explaining them through familiar analogies. A user provides a concept they want to understand and selects a familiar analogy world (e.g., "restaurant", "sports", "movies"). An AI model then generates a structured, meaningful analogy that maps elements of the original concept to elements of the chosen world. The application renders this analogy as a visual flowchart/mental model, provides a written explanation, identifies where the analogy breaks down, and offers AI-generated practice questions tied specifically to the generated analogy.

The system is designed around a guest-first experience: users can generate and experience one full analogy without creating an account. Authenticated users gain the ability to save analogies, build a personal library, and practice their understanding over time.

---

## Glossary

- **User**: Any person interacting with the application (guest or authenticated).
- **Guest**: A User who has not authenticated. Allowed to generate and fully view exactly one Analogy without authentication. Guests do NOT have access to Practice Mode.
- **Authenticated_User**: A User who has registered and logged in.
- **Concept**: The text input provided by the User describing what they want to understand (e.g., "How does an API request travel from frontend to backend?"). The Concept may be a word, phrase, question, paragraph, explanation, or any subject the User wants to understand. Accepts 1–5,000 characters. The User is not required to phrase it as a question.
- **Analogy_World**: A named category or domain chosen by the User as the basis for the analogy (e.g., "Restaurant", "Sports", "Movies").
- **Analogy**: The structured AI-generated output that maps Concept elements to Analogy_World elements.
- **Analogy_Title**: A concise, concept-focused title for a generated Analogy. Derived from the Concept input, not from the Analogy_World. Must represent what the User wants to understand (e.g., "APIs", "HTTP Requests", "Database Normalization"). Must NOT include analogy-world names (e.g., "APIs as a Restaurant" is invalid).
- **Analogy_Node**: A single element within the Analogy (e.g., a concept component mapped to an analogy element).
- **Analogy_Mapping**: The relationship between a Concept component and its corresponding Analogy_Node.
- **Analogy_Relationship**: A directional or associative link between two Analogy_Nodes that represents a real relationship in the Concept.
- **Visual_Model**: The frontend rendering of the Analogy as a flowchart or mental model diagram built from Analogy_Nodes and Analogy_Relationships.
- **Explanation**: A written narrative generated by AI that describes the Analogy and how it relates to the Concept.
- **Limitation**: A specific point where the Analogy diverges from or misrepresents the Concept, generated by AI.
- **Practice_Session**: An interactive AI-generated Q&A session tied to a specific saved Analogy. Each completed batch of questions creates one Practice_Session record. Practice_Sessions are never overwritten — each practice attempt creates a new record.
- **Library**: The authenticated User's collection of saved Analogies, displayed as "My Library" or "My Analogies".
- **AI_Service**: The backend layer that communicates with the external LLM API to generate Analogies, Explanations, Limitations, and Practice questions.
- **AI_Response**: Structured JSON data returned by the AI_Service after validation.
- **LLM_API**: The external large language model API provider called by the AI_Service.
- **Backend**: The Node.js + Express server that handles API requests, authentication, database access, and the AI_Service layer.
- **Frontend**: The React + Vite single-page application served to the User's browser.
- **Database**: The MongoDB instance used to persist User, Analogy, and Practice_Session data.
- **Session_Token**: A secure credential issued to an Authenticated_User after login, used to authorize subsequent requests.
- **Guest_Session**: Temporary client-side state (sessionStorage) holding the Guest's generated Analogy data for potential transfer to an authenticated account. Separate from Guest_ID, which persists across browser sessions.
- **Guest_ID**: A persistent anonymous identifier stored in a long-lived browser cookie, used by the Backend to track whether an unauthenticated visitor has consumed their one free analogy-generation opportunity.
- **Reset_Token**: A secure, single-use, time-limited token generated by the Backend and associated with a User's email address for the purpose of password reset.
- **Email_Service**: The backend module responsible for composing and sending transactional emails (e.g., password reset links). The email provider is configured via environment variables and can be replaced without changing other backend modules.
- **Practice_Question**: A structured AI-generated question containing: question text, question type, answer options (for multiple-choice), expected answer, explanation of the correct answer, the relevant Analogy_Mapping that supports the answer, and encouraging feedback for incorrect responses.
- **Practice_Evaluation**: The structured AI-generated result of evaluating a User's answer to a Practice_Question, containing: a correctness indicator, feedback text, the correct answer, the correct answer explanation, the relevant analogy mapping reference, an encouraging message, and any identified misconception or weak area.
- **Analogy_World_List**: The backend-maintained, configurable list of available Analogy_World categories presented to users in the selector. The list is stored in backend configuration (not hardcoded in the frontend) and can be updated without frontend changes.
- **Meaningfulness_Validator**: A backend service that evaluates whether a Concept input represents a meaningful, actionable subject for analogy generation, before the full analogy-generation request is made. Returns structured data: valid/invalid, reason, optional user-facing message.

## Requirements

---

### Requirement 1: Concept and Analogy World Input

**User Story:** As a User, I want to enter a concept, question, paragraph, or explanation I want to understand and choose a familiar analogy world, so that the system can generate a relevant analogy for me.

#### Acceptance Criteria

1. THE Frontend SHALL provide a text input field accepting between 1 and 5,000 characters for the User to enter a Concept.
2. THE Frontend SHALL communicate that the User may enter a concept, question, paragraph, explanation, or something they want help understanding — the input is NOT required to be phrased as a question.
3. THE Frontend SHALL provide a selector for the User to choose an Analogy_World from the Analogy_World_List returned by the Backend; the Frontend SHALL NOT hardcode the list of world categories.
4. WHEN the User submits a Concept that is empty (0 characters), THE Frontend SHALL display an inline validation message stating that a Concept is required and prevent form submission.
5. WHEN the User submits a Concept that exceeds 5,000 characters, THE Frontend SHALL display an inline validation message and prevent form submission.
6. WHEN the User submits the form without selecting an Analogy_World, THE Frontend SHALL display an inline validation message prompting the User to select an Analogy_World and prevent form submission.
7. WHEN the User submits a non-empty Concept of 1–5,000 characters with an Analogy_World selected, THE Frontend SHALL send the generation request to the Backend.
8. THE Backend SHALL provide an endpoint that returns the current Analogy_World_List; THE Frontend SHALL fetch this list on application load and use it to populate the Analogy_World selector.

---

### Requirement 2: AI Analogy Generation

**User Story:** As a User, I want the system to generate a structured analogy from my concept and chosen world, so that I can understand the concept through something familiar.

#### Acceptance Criteria

1. WHEN the User submits a valid Concept and Analogy_World, THE Backend SHALL first pass the Concept to the Meaningfulness_Validator before invoking the full analogy-generation LLM request.
2. THE Meaningfulness_Validator SHALL determine whether the Concept represents a meaningful, actionable subject (concept, question, explanation, topic, process, or subject) that can reasonably be transformed into an analogy; it SHALL NOT use a hardcoded blacklist of words.
3. IF the Meaningfulness_Validator determines the Concept is not meaningful (e.g., random characters, keyboard mashing), THE Backend SHALL return a structured error response to the Frontend with a user-friendly message asking the User to provide a meaningful concept, question, explanation, or topic; THE Backend SHALL NOT proceed to the full analogy-generation request.
4. THE Meaningfulness_Validator SHALL be isolated in a dedicated backend module so that the validation mechanism can be changed without affecting the main analogy-generation service.
5. THE Meaningfulness_Validator SHALL return structured data containing: a valid/invalid indicator, a reason or category, and an optional user-facing message.
6. WHEN the Concept passes the Meaningfulness_Validator, THE Backend SHALL send a structured prompt to the LLM_API requesting a JSON-formatted AI_Response containing: an Analogy_Title, Analogy_Nodes, Analogy_Mappings, Analogy_Relationships, an Explanation, and Limitations.
7. THE AI_Service SHALL never hardcode analogy elements; all Analogy_Nodes, Analogy_Mappings, and Analogy_Relationships SHALL be dynamically generated by the LLM_API for each individual request.
8. WHEN the LLM_API returns a response, THE AI_Service SHALL validate that the response contains at minimum: a non-empty Analogy_Title string, a non-empty list of Analogy_Nodes (minimum 3 nodes), a non-empty list of Analogy_Mappings (minimum 1 mapping), a non-empty Explanation string, and a non-empty Limitations list (minimum 1 item).
9. IF the LLM_API response fails validation, THEN THE AI_Service SHALL retry the request up to 2 additional times before returning an error to the Frontend, with each retry using the same original Concept and Analogy_World inputs.
10. IF all LLM_API attempts fail validation, THEN THE Backend SHALL return a structured error response to the Frontend with a user-readable message indicating that analogy generation failed and the User should try again.
11. IF the LLM_API does not return a response within 30 seconds, THEN THE AI_Service SHALL treat the request as a failed attempt and apply the retry logic defined in criterion 9.
12. WHEN the Frontend receives a valid AI_Response, THE Frontend SHALL display the Visual_Model, Explanation, and Limitations to the User within 2 seconds of receiving the response.
13. THE AI_Response SHALL support a variable number of Analogy_Nodes (minimum 3, maximum 20).
14. THE AI_Response SHALL include a `flow` field on Analogy_Relationships where a directional sequence is meaningful to the Concept.
15. THE Backend SHALL never expose the LLM_API key in any response sent to the Frontend.
16. THE AI_Service SHALL be implemented as a provider-agnostic abstraction that accepts a structured request and returns a validated AI_Response; the specific LLM provider SHALL be configured via environment variables and replaceable without changing the Frontend or other Backend routes.

### Requirement 3: Visual Model Rendering

**User Story:** As a User, I want to see the analogy displayed as a visual flowchart or mental model, so that I can understand the structure and relationships in the concept at a glance.

#### Acceptance Criteria

1. WHEN the Frontend receives a valid AI_Response, THE Frontend SHALL render a Visual_Model using the Analogy_Nodes and Analogy_Relationships from the AI_Response within 2 seconds of receiving the response.
2. THE Frontend SHALL render each Analogy_Node as a labeled node displaying both the Concept component label and the Analogy_World element label, with each label truncated at 60 characters.
3. THE Frontend SHALL render each Analogy_Relationship as a directional or associative edge connecting exactly two distinct Analogy_Nodes.
4. WHEN an Analogy_Relationship includes a `flow` value, THE Frontend SHALL render the edge with a directional arrow indicating sequence.
5. WHEN an Analogy_Relationship does not include a `flow` value, THE Frontend SHALL render the edge without a directional arrow.
6. THE Visual_Model renderer SHALL support layouts with between 3 and 20 Analogy_Nodes such that no two nodes visually overlap and no node is clipped outside the container bounds.
7. THE Frontend SHALL NOT assume a fixed number of Analogy_Nodes or Analogy_Relationships when rendering the Visual_Model.
8. WHEN the User's viewport width is less than 768px, THE Frontend SHALL render the Visual_Model in a scrollable container so that all nodes remain accessible.
9. IF the AI_Response contains fewer than 3 or more than 20 Analogy_Nodes, THEN THE Backend SHALL reject the response as invalid and apply the retry logic defined in Requirement 2.
10. THE Frontend SHALL use React Flow as the rendering library for the Visual_Model.
11. THE Frontend SHALL use the Dagre layout algorithm to automatically position Analogy_Nodes; node positions SHALL be computed at render time and SHALL NOT be stored in the Database.
12. THE Frontend SHALL pass the Analogy_Nodes and Analogy_Relationships from the AI_Response directly to the React Flow renderer.
13. THE Frontend SHALL use custom React Flow node components and custom styling so that the Visual_Model matches Relate's visual identity; the default React Flow appearance SHALL NOT define the final design.
14. THE selected Analogy_World SHALL influence the visual treatment of the Visual_Model. The visual treatment may include node styling, decorative motifs, accent treatment, edge/connector styling, background/decorative elements, and other presentation details. The semantic AI_Response structure remains unchanged and SHALL NOT contain visual styling properties. The renderer SHALL remain generic and SHALL support worlds not explicitly represented by a dedicated theme through a fallback theme. React Flow remains the rendering library. Dagre remains responsible for layout. Node positions remain computed at render time and are NEVER persisted to the Database.

---

### Requirement 4: Explanation and Limitations Display

**User Story:** As a User, I want to read a written explanation of the analogy and understand where it breaks down, so that I gain accurate understanding and know the limits of the comparison.

#### Acceptance Criteria

1. WHEN the Analogy is displayed, THE Frontend SHALL render the Explanation text in a section visually adjacent to the Visual_Model, with both sections visible without horizontal scrolling on viewports 320px wide or greater.
2. WHEN the Analogy is displayed, THE Frontend SHALL render each Limitation as a separate list item within a section labeled "Where This Analogy Breaks Down", with each item displayed on its own line and preceded by a visual indicator such as a bullet or numbered marker.
3. THE AI_Service SHALL ensure the Explanation text contains at least one explicit mention of the User's Concept by name and at least one explicit mention of the selected Analogy_World by name.
4. THE AI_Service SHALL ensure each generated Analogy includes a Limitations list containing between 1 and 10 items.
5. WHEN the Analogy response is received, THE Frontend SHALL render the Explanation and Limitations fields as formatted text content, such that no raw JSON syntax characters (including braces, brackets, or quotation marks from the data structure) are visible to the User.
6. IF the Analogy response is received with an empty or absent Explanation field, THEN THE Frontend SHALL display an error message indicating the explanation could not be loaded and shall not render the Limitations section.

### Requirement 5: Analogy Modification and Regeneration

**User Story:** As a User, I want to regenerate, simplify, expand, or try a different analogy world for my concept, so that I can find the explanation that works best for me.

#### Acceptance Criteria

1. WHEN an Analogy has been generated or when an Authenticated_User opens a saved Analogy from the Library, THE Frontend SHALL display controls allowing the Authenticated_User to: regenerate the current Analogy, simplify the Analogy, add more detail to the Analogy, or select a different Analogy_World.
2. WHEN the User selects "Simplify", THE Backend SHALL send a prompt to the LLM_API requesting a simplified version of the existing Analogy with a node count no greater than 50% of the current node count, with a minimum of 1 node retained.
3. WHEN the User selects "More Detail", THE Backend SHALL send a prompt to the LLM_API requesting an expanded version of the existing Analogy with at least 1 additional Analogy_Node and 1 additional Analogy_Relationship, up to a maximum of 50 nodes.
4. WHEN the User selects "Regenerate", THE Backend SHALL request a new Analogy from the LLM_API for the same Concept and Analogy_World; the new Analogy SHALL differ from the immediately preceding Analogy in at least one node or relationship.
5. WHEN the User selects a different Analogy_World, THE Frontend SHALL update the Analogy_World selector to the newly selected value and submit a new generation request using the same Concept and the updated Analogy_World.
6. THE Backend SHALL pass the modification type (simplify, expand, regenerate) and the current node count as parameters to the AI_Service so that the prompt is adjusted accordingly.
7. WHEN a modification request is in progress, THE Frontend SHALL display a loading indicator and disable the modification controls until the response is received or the request fails.
8. IF a modification request fails, THEN THE Backend SHALL return a structured error response, and THE Frontend SHALL re-enable the modification controls and display an error indication to the User.
9. IF the User attempts to simplify an Analogy that already contains only 1 node, THEN THE Frontend SHALL display a message indicating the Analogy cannot be simplified further and SHALL NOT submit the simplify request.
10. WHEN a modification produces a new AI-generated Analogy, the Analogy_Title SHALL remain derived from the original Concept unless the Concept itself changes; the Analogy_World SHALL NOT be used to generate or alter the Analogy_Title.

### Requirement 6: Guest Experience

**User Story:** As a Guest, I want to generate and fully experience exactly one Analogy without creating an account, so that I can evaluate whether the product is useful before committing to registration.

#### Acceptance Criteria

1. THE Frontend SHALL allow a Guest to enter a Concept, select an Analogy_World, generate an Analogy, view the Visual_Model, read the Explanation, and view the Limitations without requiring authentication.
2. THE Backend SHALL process exactly one analogy-generation request from a Guest without requiring a Session_Token.
3. THE Backend SHALL assign a Guest_ID to each unauthenticated visitor by setting a persistent browser cookie on the first visit; the cookie SHALL have a long lifetime (at minimum 30 days) so that the Guest_ID persists across browser sessions.
4. THE Backend SHALL track whether each Guest_ID has consumed its one free analogy-generation opportunity in the Database or a persistent store.
5. WHEN a Guest submits an analogy-generation request, THE Backend SHALL look up the Guest_ID: IF the free opportunity has not been consumed, allow generation and mark it as consumed; IF the free opportunity has already been consumed, reject the request with an error response indicating that authentication is required to generate another Analogy.
6. THE Frontend SHALL NOT be relied upon to enforce the one-free-Analogy limit; the Backend is the authoritative enforcement point.
7. THE Frontend SHALL display the Guest's generated Analogy (Visual_Model, Explanation, Limitations) before showing any account creation or login prompt.
8. WHEN the Guest's Analogy has been displayed, THE Frontend SHALL present a prompt offering the Guest options to: Create Account, Log In, or Dismiss.
9. IF the Guest dismisses the prompt, THE Frontend SHALL hide the prompt but SHALL NOT allow the Guest to generate another Analogy without authentication; the Guest may continue viewing their current Analogy.
10. Closing and reopening the browser SHALL NOT reset the Guest's free-use state as long as the Guest_ID cookie remains available in the browser.
11. THE system SHALL acknowledge that the one-free-Analogy limit cannot be guaranteed per human (users may clear cookies, use incognito, or use another device); this is acceptable for v1 and SHALL NOT be addressed through invasive device fingerprinting.
12. Guests SHALL NOT have access to Practice Mode; Practice is available only to Authenticated_Users.
13. Guests SHALL NOT be able to save Analogies to a Library; saving requires authentication.
14. IF a Guest attempts to generate a second Analogy (e.g., by manipulating the frontend), THE Backend SHALL reject the request and return an appropriate error.

### Requirement 7: User Registration and Authentication

**User Story:** As a Guest, I want to create an account, so that I can save analogies and track my learning progress over time.

#### Acceptance Criteria

1. THE Backend SHALL provide a registration endpoint that accepts a name, email address, password, and optional guestAnalogy payload.
2. WHEN a registration request is received, THE Backend SHALL validate that the email address contains exactly one "@" symbol, a non-empty local part before the "@", and a domain part after the "@" that contains at least one "." character; if invalid, return a 400 response with message: "Please enter a valid email address."
3. WHEN a registration request is received, THE Backend SHALL validate that the password is at least 8 characters and no more than 128 characters long; if shorter than 8, return: "Password must be at least 8 characters."; if longer than 128, return: "Password must be no more than 128 characters."
4. WHEN a registration request is received with an empty or absent name field, THE Backend SHALL return a 400 response with message: "Please enter your name."
5. WHEN a registration request is received with a name field that exceeds 100 characters, THE Backend SHALL return a 400 response specifying that the name is too long.
6. WHEN a registration request is received with an email address that already exists in the Database, THE Backend SHALL return an error response with message: "An account with this email is already registered."
7. THE Backend SHALL hash the User's password using a secure one-way hashing algorithm before storing it in the Database; the plaintext password SHALL never be stored.
8. THE Backend SHALL never store the Confirm Password value.
9. WHEN a User submits valid registration credentials, THE Backend SHALL create a User record in the Database and return a Session_Token.
10. THE Frontend registration form SHALL contain four fields: Name, Email, Password, and Confirm Password.
11. WHEN the Confirm Password field is empty at submission, THE Frontend SHALL display: "Please confirm your password."
12. WHEN the Password and Confirm Password fields do not match, THE Frontend SHALL display: "Passwords do not match." and prevent form submission.
13. THE Frontend SHALL display field-specific validation messages for each invalid field; it SHALL NOT show a single generic error for all validation failures.
14. THE Backend SHALL provide a login endpoint that accepts an email address and password.
15. WHEN a login request is received with a valid email and password combination, THE Backend SHALL return a Session_Token.
16. IF a login request is received with an invalid email or password, THEN THE Backend SHALL return a generic error message that does not distinguish whether the email or password was incorrect.
17. THE Backend SHALL provide a logout endpoint that invalidates the User's Session_Token.
18. THE Session_Token SHALL be transmitted using an HttpOnly cookie; it SHALL NOT be stored in localStorage or sessionStorage.
19. THE Backend SHALL provide a protected endpoint that returns the current authenticated User's profile data (name, email, createdAt) when a valid Session_Token is present.
20. IF a request is received on a protected endpoint without a Session_Token or with an expired or invalid Session_Token, THEN THE Backend SHALL return a 401 Unauthorized response.
21. THE Backend SHALL only collect name, email, and password from the User during registration; no additional personal data SHALL be requested.
22. THE Login form SHALL require both Email and Password fields; IF either field is empty, THE Frontend SHALL display an appropriate validation message and prevent submission.

### Requirement 8: Saving Analogies

**User Story:** As an Authenticated_User, I want to save a generated analogy to my library, so that I can return to it and practice it later.

#### Acceptance Criteria

1. WHEN an Authenticated_User views a generated Analogy, THE Frontend SHALL display a "Save" button.
2. WHEN the User clicks "Save", THE Frontend SHALL send a save request to the Backend containing: Analogy_Title, Concept, Analogy_World, and all AI_Response data (Analogy_Nodes, Analogy_Mappings, Analogy_Relationships, Explanation, Limitations).
3. WHEN the Backend receives a valid save request from an Authenticated_User with all required fields present and non-empty, THE Backend SHALL store a new Analogy record in the Database (including Analogy_Title) and return a response containing the saved Analogy's unique identifier.
4. THE Backend SHALL set the `createdAt` and `updatedAt` timestamps on the Analogy record to the current server time at the moment of creation.
5. WHEN the Backend returns a success response containing the saved Analogy's unique identifier, THE Frontend SHALL update the "Save" button to indicate the Analogy has been saved and disable further duplicate save requests for the same Analogy.
6. WHEN an Authenticated_User regenerates or modifies a previously saved Analogy, THE Frontend SHALL offer the option to save the updated version; WHEN the User confirms, THE Frontend SHALL send an update request to the Backend containing the Analogy's unique identifier and the new AI_Response data, and THE Backend SHALL update the existing Analogy record's data and `updatedAt` timestamp.
7. IF a save request is received without a valid Session_Token, THEN THE Backend SHALL return a 401 Unauthorized response and SHALL NOT create or modify any Analogy record.
8. IF a save request is received with one or more required fields absent or empty, THEN THE Backend SHALL return a 400 Bad Request response specifying which fields are invalid.
9. IF the Database operation fails during a save or update request, THEN THE Backend SHALL return a 500 Internal Server Error response, and THE Frontend SHALL display an error message indicating the Analogy could not be saved and allow the User to retry.

### Requirement 9: Library (My Library / My Analogies)

**User Story:** As an Authenticated_User, I want to view all my saved analogies in one place, so that I can quickly find and revisit concepts I have studied.

#### Acceptance Criteria

1. THE Frontend SHALL provide a "My Library" section (labeled "My Library" or "My Analogies", NOT "Projects") accessible only to Authenticated_Users.
2. WHEN an Authenticated_User navigates to "My Library", THE Frontend SHALL request the User's saved Analogies from the Backend.
3. WHEN the Backend receives a valid Library request, THE Backend SHALL return all Analogy records associated with the authenticated User's account, ordered by creation date descending.
4. THE Frontend SHALL display each saved Analogy as a card showing: the Analogy_Title as the primary title, the original Concept text (truncated with ellipsis at 100 characters), the Analogy_World name, the creation date formatted as YYYY-MM-DD, and a text-based Visual_Model preview listing the first 3–4 Analogy_Node labels (concept label → analogy label) separated by line breaks; the preview SHALL NOT require rendering a graph component.
5. Each Library card SHALL provide both an "Open" action and a "Practice" shortcut action.
6. WHEN the User clicks a Library card's "Open" action, THE Frontend SHALL navigate to the individual Analogy view for that specific Analogy.
7. The individual Analogy view SHALL display: Analogy_Title, Visual_Model, Explanation, Limitations, modification controls, and a Practice button.
8. The individual Analogy view SHALL NOT be titled "My Library" or "My Analogies"; its primary heading SHALL be the Analogy_Title.
9. WHEN the User clicks a Library card's "Practice" shortcut, THE Frontend SHALL navigate to the individual Analogy view with Practice Mode automatically activated.
10. WHEN the User's Library contains no saved Analogies, THE Frontend SHALL display an empty state message encouraging the User to generate and save their first Analogy.
11. IF the Session_Token in the Library request is absent, expired, or invalid, THEN THE Backend SHALL reject the request with a 401 Unauthorized response and return no Analogy data.
12. IF the Backend fails to retrieve the User's Library data, THEN THE Frontend SHALL display an error message and retain the previously displayed page state.

### Requirement 10: Practice Mode

**User Story:** As an Authenticated_User, I want to practice my understanding of a saved analogy through an interactive, supportive learning experience, so that I can verify and deepen my understanding of the original concept and learn from my mistakes.

#### Acceptance Criteria

1. THE Frontend SHALL provide a standalone "Practice" navigation option accessible to Authenticated_Users from the main navigation.
2. WHEN the User navigates to the Practice section via main navigation, THE Frontend SHALL display a page with a message such as "Choose an analogy to test your understanding" and present a list of the User's saved Analogies for selection.
3. WHEN the User selects a saved Analogy from the Practice navigation, THE Frontend SHALL begin a Practice Session for that specific Analogy.
4. The individual saved Analogy view SHALL also include a "Practice" button that starts a Practice Session for that specific Analogy directly (shortcut path).
5. Practice SHALL require authentication; Guests SHALL NOT have access to Practice Mode.
6. WHEN a Practice Session begins, THE Backend SHALL send the Concept, Analogy_World, Analogy_Nodes, Analogy_Mappings, Analogy_Relationships, Explanation, and Limitations to the AI_Service to generate Practice_Questions.
7. A standard Practice Session SHALL contain a maximum of 5 questions; the AI_Service SHALL generate up to 5 questions unless the Analogy is too simple to support 5 genuinely distinct questions, in which case it SHALL generate as many as possible (minimum 1).
8. THE AI_Service SHALL generate Practice_Questions that are specifically grounded in the Concept and the generated Analogy; questions SHALL NOT be generic knowledge questions about the Concept topic alone.
9. THE AI_Service SHALL vary question styles including: basic understanding, Concept→Analogy mapping, Analogy→Concept mapping, application/scenario, reasoning, and misconception/transfer questions.
10. THE AI_Service SHALL return each Practice_Question as structured data containing: question text, question type (short-answer or multiple-choice), answer options for multiple-choice (between 2 and 6 options, exactly one correct), expected answer text, an explanation of the correct answer, the label of the relevant Analogy_Mapping, and an encouraging message for an incorrect answer.
11. THE Frontend SHALL present one Practice_Question at a time.
12. For multiple-choice questions, THE Frontend SHALL render selectable answer options; the User submits by selecting an option.
13. WHEN the User submits an answer, THE Backend SHALL send the Practice_Question and User answer to the AI_Service for evaluation and return a Practice_Evaluation.
14. THE AI_Service SHALL return a Practice_Evaluation as structured data containing: a correctness indicator (correct or incorrect), feedback text, the correct answer, the correct answer explanation, the label of the relevant Analogy_Mapping, an encouraging message, and an optional misconception or weak area (may be null).
15. WHEN the Practice_Evaluation indicates the answer is correct, THE Frontend SHALL render: the selected option with a green background and green outline, a clear checkmark indicator, the text "Correct ✓", and a collapsed "▾ See explanation" control; the explanation SHALL be hidden by default and visible only when the User expands it.
16. WHEN the Practice_Evaluation indicates the answer is incorrect, THE Frontend SHALL render: the selected option with a red background and red outline, a clear cross/error indicator, the text "Not quite ✕", and a collapsed "▾ See explanation" control; when expanded, the explanation SHALL show the correct answer, the correct answer explanation, the relevant Analogy_Mapping, and the encouraging message.
17. THE Frontend SHALL NOT immediately display a full explanation after an answer; the explanation SHALL be behind the expandable "See explanation" control for BOTH correct and incorrect answers.
18. After evaluation (correct or incorrect), THE Frontend SHALL display a "Continue" control to proceed to the next question.
19. IF the AI_Service does not return a Practice_Evaluation within 15 seconds, THEN THE Backend SHALL return a timeout error, and THE Frontend SHALL display an error message and allow the User to retry the current question without losing Practice Session state.
20. THE Frontend SHALL render all Practice_Evaluation fields using dedicated UI components; THE Frontend SHALL NOT render raw AI text directly as unstructured content.
21. IF the AI_Service returns an error or does not return valid Practice_Questions within 15 seconds of session start, THE Backend SHALL return an error response, and THE Frontend SHALL display an error message and offer a retry option.
